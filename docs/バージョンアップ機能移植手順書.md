# バージョンアップ機能 移植手順書

チョコスケの「アプリの更新」機能（新しいバージョンを公開すると「新しいバージョンがあります [後で] [更新]」のスナックバーを出し、利用者が「更新」を押したときだけ切り替える仕組み）を、リポジトリテンプレートや他のアプリに移植するための手順書。

移植元: `5188fa7` 時点の `apps/frontend`（主に `b43301f feat: ask before switching to a new app version with an update snackbar`）。

## 1. 概要

### 動作

- 新しいバージョンを公開すると、画面下部に「新しいバージョンがあります」のスナックバー（「後で」「更新」ボタン付き）を表示する。閉じるまで消えない。
- 「更新」: 新しいバージョンに切り替えて再読み込みする。
- 「後で」: スナックバーを閉じる。次にアプリを開いたときに再び表示する。
- 入力中の内容を失わないよう、自動では切り替えない。
- 新しいバージョンの確認は、アプリを開いたとき・アプリが前面に戻ったとき・1時間ごとに行う（ホーム画面に追加したアプリはバックグラウンドから戻るだけで、ページを読み込み直さないことが多いため）。
- ほかのスナックバー（エラー等）の表示中は隠れ、それが閉じると再び出る。

### しくみ

フロントエンドだけで完結する。バックエンドの API・DB・ランタイム固有のコードは使わない。

1. ビルドのたびに `vite-plugin-pwa` が Service Worker（SW）を生成し、その中にビルド成果物のファイル一覧（リビジョン付き）を埋め込む。中身が1バイトでも変わると SW ファイルが変わる＝新バージョンとして検出される。
2. ブラウザは新しい SW をインストールするが、`registerType: 'prompt'` なので有効化せず待機（waiting）させる。
3. `useRegisterSW`（`workbox-window`）が待機中の SW を検出すると `needRefresh` が `true` になり、スナックバーが出る。
4. 「更新」で `updateServiceWorker()` が SW に `SKIP_WAITING` メッセージを送る → SW が `skipWaiting()` → `clients.claim()` で制御を引き継ぐ → ページが再読み込みされ、新しいバージョンで開き直す。
5. 「後で」は `needRefresh` を `false` にするだけ。SW は待機したままなので、次にページを読み込んだとき再び検出されてスナックバーが出る。

### 適用範囲

| 観点                                         | 共通で使えるか | 理由・条件                                                                                                                                          |
| -------------------------------------------- | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 公開用アプリ / 業務用アプリ                  | 使える         | 認証・利用者・業務ロジックに依存しない。PWA（ホーム画面追加・オフライン）を使わない業務用アプリでも、更新検出のためだけに SW を置けば動く。         |
| Cloudflare Workers / Node.js（オンプレミス） | 使える         | ランタイムはビルド済みの静的ファイル（`sw.js` 等）を配信するだけ。ランタイム側のコード変更は不要。ただし「4. ランタイム別の前提条件」を満たすこと。 |

## 2. 前提

- フロントエンドが Vite（Vite+）＋ Vue 3 ＋ Vuetify で、ビルド成果物が SPA として配信されている。
- フロントエンドとAPIが同一オリジン（フロントエンドは `/`、API は `/api`）。
- 別の UI ライブラリの場合は、「3-5. スナックバー」を同等のコンポーネントに置き換える（ロジックは `usePwaUpdate` に閉じている）。

## 3. 移植手順

移植先がすでに独自の SW（プッシュ通知等）を持つかどうかで、SW の作り方を2つから選ぶ。

| 移植先の状態                                                    | 選ぶ方式                                       |
| --------------------------------------------------------------- | ---------------------------------------------- |
| SW がない／PWA 化していない（テンプレート・業務用アプリに多い） | **方式A: `generateSW`**（SW を書かない）       |
| 独自の SW がある（プッシュ通知など。チョコスケはこちら）        | **方式B: `injectManifest`**（SW を自分で書く） |

### 3-1. 依存パッケージの追加

ルートの `pnpm-workspace.yaml` の `catalog:` に追加する（すでにあるものは不要）。

```yaml
catalog:
  vite-plugin-pwa: ^1.3.0
  workbox-window: ^7.4.1
  # 方式Bのみ
  workbox-precaching: ^7.4.1
  workbox-routing: ^7.4.1
```

`apps/frontend/package.json` の `devDependencies` に追加する。

```json
"vite-plugin-pwa": "catalog:",
"workbox-window": "catalog:",
"workbox-precaching": "catalog:",
"workbox-routing": "catalog:"
```

（`workbox-precaching` / `workbox-routing` は方式Bのみ。）その後 `vp install`。

`workbox-window` は `virtual:pwa-register/vue`（`useRegisterSW`）が実行時に使う。入れ忘れるとビルドで解決エラーになる。

### 3-2. `vite.config.ts` に `VitePWA` を追加

#### 方式A: `generateSW`

```ts
import { VitePWA } from 'vite-plugin-pwa'

export default defineConfig({
  plugins: [
    vue(),
    vuetify({ autoImport: true }),
    // Service worker: detects a new build and waits for the person to tap "更新"
    // (`registerType: 'prompt'`, `usePwaUpdate`). `/api` is never cached. Off in `vp dev`.
    VitePWA({
      registerType: 'prompt',
      workbox: {
        globPatterns: ['**/*.{js,css,html,woff2,png,svg}'],
        // The SPA fallback must not answer the API.
        navigateFallbackDenylist: [/^\/api\//],
      },
      // PWA (home screen install) not needed: no manifest. Set one here to make it installable.
      manifest: false,
    }),
  ],
})
```

- `registerType: 'prompt'` にすると、生成される SW は `skipWaiting` せず、`SKIP_WAITING` メッセージを受けたときだけ切り替わる（Workbox が自動で組み込む）。SW を自分で書く必要はない。
- ホーム画面に追加できる PWA にしたい場合は `manifest` を設定する（チョコスケの `apps/frontend/vite.config.ts` を参照）。

#### 方式B: `injectManifest`（チョコスケの方式）

```ts
VitePWA({
  strategies: 'injectManifest',
  srcDir: 'src',
  filename: 'sw.ts',
  registerType: 'prompt',
  injectManifest: {
    globPatterns: ['**/*.{js,css,html,woff2,png,svg}'],
  },
  manifest: { /* PWA にする場合 */ },
}),
```

### 3-3. Service Worker（方式Bのみ）

`apps/frontend/src/sw.ts` に次を入れる。既存の SW がある場合は、**`install` で `skipWaiting()` している処理を必ず削除**して `message` ハンドラに置き換える（残っていると確認なしに切り替わる）。

```ts
import {
  cleanupOutdatedCaches,
  createHandlerBoundToURL,
  precacheAndRoute,
} from 'workbox-precaching'
import { NavigationRoute, registerRoute } from 'workbox-routing'

// Only the bits of the service worker globals used here (the `webworker` lib conflicts with `DOM`).
interface ExtendableEvent extends Event {
  waitUntil: (promise: Promise<unknown>) => void
}
interface ServiceWorkerScope {
  __WB_MANIFEST: (string | { url: string; revision: string | null })[]
  skipWaiting: () => Promise<void>
  clients: { claim: () => Promise<void> }
  addEventListener: ((type: 'activate', listener: (event: ExtendableEvent) => void) => void) &
    ((type: 'message', listener: (event: MessageEvent) => void) => void)
}

const sw = self as unknown as ServiceWorkerScope

// A new version waits until the person taps "更新" on the snackbar (`registerType: 'prompt'`,
// `usePwaUpdate`), which sends this message; the page reloads once it has taken over. Taking over
// unasked would swap the cached files under a page still running the old build.
sw.addEventListener('message', (event) => {
  if ((event.data as { type?: string } | null)?.type === 'SKIP_WAITING') void sw.skipWaiting()
})
sw.addEventListener('activate', (event) => event.waitUntil(sw.clients.claim()))

// Written out as `self.__WB_MANIFEST`: the build looks for exactly that to inject the file list.
precacheAndRoute((self as unknown as ServiceWorkerScope).__WB_MANIFEST)
cleanupOutdatedCaches()
registerRoute(
  new NavigationRoute(createHandlerBoundToURL('index.html'), { denylist: [/^\/api\//] }),
)
```

- `self.__WB_MANIFEST` は、ビルドがこの文字列を探してファイル一覧を埋め込むため、この書き方のまま残す。
- `/api` は `denylist` で除外し、キャッシュしない。

### 3-4. 型宣言

フロントエンドの型宣言ファイル（チョコスケは `apps/frontend/src/env.d.ts`、テンプレートによっては `vite-env.d.ts`）に1行追加する。

```ts
/// <reference types="vite-plugin-pwa/vue" />
```

`virtual:pwa-register/vue` の型がこれで解決される。

### 3-5. コンポーザブル `usePwaUpdate`

`apps/frontend/src/composables/usePwaUpdate.ts` を新規作成する（チョコスケのものをそのまま使える）。

```ts
import { useRegisterSW } from 'virtual:pwa-register/vue'

// Updating the app (docs/spec.md "共通ルール > 画面 > アプリの更新"). The browser looks for a new
// service worker only when a page loads, and an app on a phone mostly comes back from the
// background without one, so it's also checked when the app comes to the front and every hour.
// A new version waits for the person to tap "更新" (a form may be half filled in).

const CHECK_INTERVAL_MS = 60 * 60 * 1000

/** Called once, from `App.vue`. Off in `vp dev` (no service worker there). */
export const usePwaUpdate = () => {
  const { needRefresh, updateServiceWorker } = useRegisterSW({
    onRegisteredSW: (_url, registration) => {
      if (!registration) return
      // Rejects offline; the next check tries again.
      const check = () => void registration.update().catch(() => {})
      document.addEventListener('visibilitychange', () => {
        if (document.visibilityState === 'visible') check()
      })
      setInterval(check, CHECK_INTERVAL_MS)
    },
  })

  /** Hands over to the new version; the page reloads once it has taken over. */
  const update = () => void updateServiceWorker()

  return { needRefresh, update }
}
```

- `useRegisterSW` が SW の登録も行うので、`main.ts` 等で別途 `navigator.serviceWorker.register()` しない（二重登録になる）。
- 業務用アプリで確認間隔を変えたい場合は `CHECK_INTERVAL_MS` を調整する。

### 3-6. `App.vue` にスナックバーを追加

```vue
<script setup lang="ts">
import { usePwaUpdate } from './composables/usePwaUpdate.ts'
import { useNotificationStore } from './stores/notification.ts'

const notification = useNotificationStore()
const { needRefresh, update } = usePwaUpdate()
</script>

<template>
  <v-app>
    <!-- ... -->
    <!-- A new version of the app: stays until tapped, behind any other message shown meanwhile. -->
    <v-snackbar
      :model-value="needRefresh && !notification.visible"
      location="bottom"
      :timeout="-1"
      class="snackbar--info"
    >
      新しいバージョンがあります
      <template #actions>
        <v-btn variant="text" @click="needRefresh = false">後で</v-btn>
        <v-btn variant="text" color="primary-container" @click="update">更新</v-btn>
      </template>
    </v-snackbar>
  </v-app>
</template>
```

- `!notification.visible` は、アプリ共通のスナックバー（エラー等）と重ならないようにするための条件。移植先に同等のストアがなければ `:model-value="needRefresh"` だけでよい。
- `snackbar--info` は濃いグレー背景・白文字のスタイル（チョコスケの `App.vue` の `<style scoped>` を参照）。移植先の見た目に合わせて変えてよい。
- `color="primary-container"` は移植先のテーマに無い色なら `primary` 等に変える。

## 4. ランタイム別の前提条件

ランタイム側のコード変更は不要。ただし次を満たさないと、SW が登録されない・更新が検出されないことがある。

### 共通

- **HTTPS で配信する**（`localhost` は例外）。SW は安全なコンテキストでしか動かない。HTTP で配信すると SW が登録されず、スナックバーは一切出ない（アプリ自体は動き、再読み込みで新しいバージョンになるだけ）。
- **`sw.js` と `index.html` に長期キャッシュ（`Cache-Control: max-age=...` / `immutable`）を付けない。** ハッシュ付きの `assets/*` は長期キャッシュしてよい。
- **`sw.js` を SPA フォールバックで `index.html` に置き換えない。** `sw.js` はビルド成果物（`dist/sw.js`）として存在するので、通常の静的配信で JavaScript として返れば問題ない。
- **`/api` は SW でキャッシュしない**（手順3で設定済み）。

### Cloudflare Workers（`apps/backend-worker`）

- `wrangler.jsonc` の `assets`（`directory: "../frontend/dist"`、`not_found_handling: "single-page-application"`、`run_worker_first: ["/api/*"]`）のままでよい。`sw.js` は実在ファイルなので SPA フォールバックの対象にならない。
- Workers の静的アセットは HTML / `sw.js` を長期キャッシュしない既定値なので、追加の設定は不要。`public/_headers` で `/*` に `Cache-Control` を付けている場合は `sw.js` と `index.html` を除外する。

### Node.js（`apps/backend-node`、オンプレミス）

- Hono の `serveStatic`（`@hono/node-server/serve-static`）で `dist` を配信し、見つからないパスだけ `index.html` を返す構成ならそのままでよい。
- リバースプロキシ（nginx / IIS 等）を前段に置く場合:
  - HTTPS を終端させる（社内用でも IP アドレス直の HTTP では SW が動かない）。
  - `sw.js` / `index.html` にキャッシュ期間を付けない（`try_files $uri /index.html;` の SPA フォールバックは実在ファイルを先に返すので `sw.js` は問題ない）。
  - `.webmanifest`（PWA にする場合）が `application/manifest+json` で返ることを確認する。

## 5. 動作確認

`vp dev` では SW が無効なので、本番ビルドで確認する。

1. `vp run frontend#build` でビルドし、本番と同じ構成（Workers なら `wrangler dev`、Node.js ならサーバーを起動）で開く。
2. DevTools > Application > Service Workers で SW が `activated and is running` になっていることを確認する。
3. 画面の文言など何か1か所を変えて再ビルド・再起動する。
4. タブを別のタブに切り替えて戻す（`visibilitychange`）か、再読み込みする → DevTools で新しい SW が `waiting to activate` になり、スナックバーが出る。
5. 「後で」→ スナックバーが消える。再読み込み → 再び出る。
6. 「更新」→ 再読み込みされ、変更が反映される。スナックバーは出ない。
7. 入力中のフォームがある画面でも、「更新」を押すまで切り替わらないことを確認する。
8. スマートフォンのホーム画面アプリで、デプロイ後にバックグラウンドから戻したときにスナックバーが出ることを確認する（PWA にする場合）。

## 6. 注意点

- **自動更新（`registerType: 'autoUpdate'` や `install` での `skipWaiting()`）から移行する場合**、旧バージョンを開いている端末には「更新」ボタンが無い。新しい SW は待機するため、その端末はアプリ（全タブ）を完全に閉じて開き直すまで旧バージョンのままになる。以降のバージョンからはスナックバーで更新できる。
- **API の互換性**: 「後で」を選んだ利用者は旧バージョンのフロントエンドで新しい API を呼び続ける。API の破壊的変更は、旧フロントエンドがしばらく残る前提で段階的に行う（必要なら旧クライアントを拒否するステータスを返し、フロントエンドで再読み込みを促す）。
- **プッシュ通知等で SW を使っている場合**、新しい SW が有効になるまで通知処理も旧バージョンのまま動く。VAPID 鍵の変更など SW 側の変更は、更新が行き渡るまでの期間を考慮する。
- **SW の解除**: 移植後に機能をやめる場合、SW を消すだけでは端末に残る。`self.registration.unregister()` するだけの SW を一度配信してから削除する。
